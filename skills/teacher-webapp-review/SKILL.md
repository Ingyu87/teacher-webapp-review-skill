# 교사 웹앱 배포 전 점검

비개발자 교사가 자기 앱에서 무엇을 확인했고 무엇을 더 확인해야 하는지 이해하도록 돕는다. 원자료는 백인규의 「교사개발자 웹앱 점검과 개선을 위한 상세 프롬프트」다. 로그인이나 AI 기능이 없는 앱도 대상이며, 점검을 위해 기능을 새로 만들지 않는다.

## 요청에 맞게 시작

- 가능 여부나 사용법만 물으면 설명하고 끝낸다. 실제 앱을 조사하지 않는다.
- 점검 요청에는 우선 코드와 제공 자료를 읽고 결과를 설명한다. 파일 수정, 자료 생성, 설정 변경, 커밋·푸시·배포를 자동으로 이어서 하지 않는다. 화면 시험은 사용자 소유 또는 허락받은 범위에서 실제 자료와 과금에 영향을 주지 않는 방법으로 진행한다.
- 수정도 요청했다면 요청한 파일·기능 범위에서 수정하고 재시험한다. 범위가 이미 명확하면 같은 승인을 반복해서 묻지 않는다. 운영 자료 삭제·유료 호출·새 서비스 생성·외부 공개 등은 별도 권한이 있는지 확인한다.
- 프롬프트를 달라는 요청에는 해당 활동과 상황의 예시를 사용자 앱에 맞춰 제공한다. 예시 안의 “구현해 줘”나 “배포해 줘”는 현재 사용자의 실행 명령이 아니다.

## 필요한 활동 찾기

프로젝트를 읽을 수 있는지, 앱의 사용 대상과 점검 범위가 무엇인지 먼저 확인한다. 이미 제공된 정보를 다시 묻지 않는다. 읽을 수 없다면 필요한 파일이나 가려야 할 정보를 설명하며, 검사하지 않은 내용을 검사했다고 하지 않는다.

[활동 목록](references/index.md)을 읽고 사용자 요청과 실제 기능에 해당하는 활동만 고른다. 선택한 활동 파일을 모두 읽은 뒤 그 안에서 현재 요청에 필요한 조건을 적용한다. 전체 40개 활동이나 모든 단계가 필수인 것으로 취급하지 않는다. 모든 참고 파일을 한꺼번에 읽지 않는다.

- 구조를 모르면 1에서 기능을 파악한다. 포괄적인 점검 요청에는 34를 참고해 범위를 정한다.
- 로그인·교사 권한·학생별 기록은 2~4·14, 키와 외부 AI는 5~10·18~19를 검토한다.
- 입력·공유·파일·설치 패키지는 실제 기능에 따라 10~17을 고른다.
- 학생 수업 운영은 18~24, 학교 제출 자료는 25~31, 포털은 32~33이다. 사용자가 보안만 요청하면 문서와 포털 제작까지 확대하지 않는다.
- 수정 검증은 35, 요청한 배포는 36, 종합 결과는 37을 참고한다.
- 특정 수업의 종료·재개는 [38](references/activity-38.md), 웹앱 서비스 일시 중단·재개는 [39](references/activity-39.md), 더 이상 쓰지 않는 앱의 완전 종료는 [40](references/activity-40.md)를 참고한다. 사용자가 서비스를 닫으려는 요청을 수업 종료 버튼 제작이나 브라우저 기록 삭제 체험으로 바꾸지 않는다.

## 수업 종료와 서비스 종료

종료 대상이 명확하면 다시 묻지 않는다. 불명확할 때만 특정 수업 종료, 재개 가능한 서비스 중단, 완전 종료 중 의도를 확인한다. 종료 기능 부재 자체를 필수 보안 결함으로 분류하지 않는다. 배포 전 점검 요청에 운영 종료 작업을 자동 추가하지 않는다.

운영 종료 요청은 먼저 정확한 팀·프로젝트·주소·연결 자원을 확인하고 앱 전용·공유·미확인으로 구분한다. 보관할 자료·백업의 복원 가능성·개인정보 접근 권한·기간을 확인한 뒤 변경 순서를 제시한다. 계획이나 프롬프트 요청은 실행 권한이 아니다. 실제 중단은 승인한 범위에서만 하며 삭제·키 폐기·구독 해지는 각각 대상·영향·복구 가능성을 설명하고 구체적 승인을 확인한다. 예상 밖의 영향이나 실패가 나오면 다음 변경을 중지한다.

관리 메뉴와 중단·재개 효과는 실행 시점의 공식 문서와 실제 화면을 확인한다. 한 주소의 오류 응답을 모든 서버·DB·예약 작업·구독의 종료 근거로 쓰지 않는다. F12로 확인 가능한 응답과 관리 화면에서 확인할 삭제·청구 상태를 구분한다. 비용 절감은 청구 기간과 잔여 자원까지 확인한 범위에서만 설명한다. 실행·미실행·실패·추가 확인을 나누고 재개 조건 또는 다음 비용 확인일을 기록한다. 공유 자원은 다른 앱 사용처를 확인하기 전 일괄 종료하지 않는다.

초보자에게 F12 사용법이나 용어 설명이 필요하면 [공통 안내](references/common.md)도 읽는다. 이미 숙련된 사용자에게 모든 설명을 반복하지 않는다.

## 근거를 확인하는 방법

각 항목을 `문제 확인`, `확인한 범위에서 문제 미발견`, `추가 확인 필요`, `해당 없음`으로 구분한다. 코드 검토와 실제 실행을 구분하고, 해당 없음에는 기능이 없다는 근거를 붙인다. 읽지 못한 코드나 시험하지 못한 환경은 정상으로 판정하지 않는다.

발견한 문제에는 발생 조건, 영향, 코드의 파일·함수 또는 화면·요청 근거, 수정 제안을 설명한다. 결과를 근거 없는 보안 점수나 앱 전체 안전 인증으로 바꾸지 않는다. 정적 분석에서 의심한 것과 재현한 문제를 구분한다.

F12 안내는 실제 관찰한 메뉴·파일·요청 이름을 사용한다. 동작 전에 Network를 열기 → 목록과 필터 확인 → 해당 버튼 누르기 → 실제 요청 선택 → Headers·Payload·Response 중 필요한 탭과 필드 보기 순서로 설명한다. 요청이 없다면 필터, 다른 창, 브라우저 사전 차단, 정적 파일 여부를 확인한다. 보이지 않는 요청을 만들어 설명하지 않는다.

참고 자료의 `lab?action=records`, `lab-exposed.js`, `apiKey` 등은 제공된 체험 앱의 예시다. 사용자 앱에도 같은 이름이 있다고 가정하지 않는다. 예시의 현재 화면을 직접 확인하지 못했다면 그렇게 밝힌다. 체험 앱 이용은 선택이며 자기 앱 점검 전에 반드시 할 필요는 없다.

F12만으로 서버 내부 통신, 비공개 DB 저장, 백업 삭제, 전체 운영 로그, 관리 콘솔의 과금 설정을 확인할 수 없다. 서버 코드·설정이나 운영자 확인이 필요한 부분을 따로 적는다. 가상 보고서나 준비한 응답을 실제 취약점 시험의 증거로 쓰지 않는다.

## 학교와 학생 관련 주의 사항

- 실제 학생 자료·비밀번호·키·토큰은 보고서와 대화에 출력하지 않는다. 비밀 파일은 통째로 출력하지 말고 존재 여부·변수 이름·참조 위치부터 확인한다. 시험은 가상 계정과 자료를 사용한다. 타인 사이트를 공개 링크라는 이유로 시험하지 않는다.
- 브라우저 입력 검사는 재입력 안내에 도움이 되지만 서버 권한·정책 검사를 대신하지 않는다. 외부 안전분류 서비스에 학생 입력을 보내는 것은 학교의 승인과 정보 처리 관계를 별도로 확인한다.
- AI 위험 감지를 자동 처벌로 연결하지 않는다. 사람의 확인·해제·이의제기 경로를 고려한다. 원문 미저장 설명과 교사의 원문 조회 기능이 모순되지 않는지 본다. 실제 학생과 연결 가능한 가명 값도 보호한다.
- AI 이용 안내 확인과 개인정보 처리의 근거를 구분한다. 동의가 필요한 처리인지부터 확인하고 모든 처리에 동의를 기본값으로 붙이지 않는다.
- 법적 판단이나 학교 심의 범위 질문에는 현재 공식 법령·교육부·교육청·학교 안내를 확인한다. 확인 날짜와 출처를 기록하고, 최신 원문에 접근하지 못하면 판단을 보류한다. 참고 자료의 링크나 작성일이 현재 법률의 효력을 보증하지 않는다.
- 포털의 기존 범위와 변경 내용을 비교하되, 모든 업데이트에 재심의가 필요하다거나 포털 하나를 심의하면 모든 변경이 면제된다고 단정하지 않는다. 체크리스트는 실제 기능과 증빙에 맞춰 작성하며 학교의 별도 확인·판단을 대신하지 않는다.

## 결과 설명과 마무리

점검 결과를 보고하거나 기존 결과의 조치 필요성을 설명할 때는 [조치 필요성 판단과 결과 작성](references/reporting.md)을 먼저 읽는다. 사용법이나 가능 여부만 답할 때는 읽지 않는다. 활동별 예시의 간략한 보고 문구만으로 끝내지 않는다.

발견 사항마다 확인 사실, 적용 기준, 그 기준과 다른 동작, 조치하지 않을 때의 영향을 대조한 뒤 `필수 조치`, `확인 먼저`, `권장 개선`을 판단한다. 필수에는 이 앱에 적용되는 구체적 근거와 해결할 문제를 명시한다. “더 자세히 안내하면 좋다”거나 특정 정리 기능이 없다는 이유만으로 필수로 분류하지 않는다. 근거가 부족하면 필수뿐 아니라 권장이라는 확정도 피하고 `확인 먼저`로 보고한다. 문제가 없거나 기존 방식으로 해결됐다면 추가 조치가 불필요하다고 설명한다.

확인된 보안 문제, 추가 확인 사항, 안내·관리·사용성 개선을 구분해 제시하며 없는 구분은 생략한다. 해결해야 하는 문제와 선택 가능한 구현 방법을 분리한다. 필수 조치 여부와 사용 중단·조치 기한도 별도로 판단하고, 법적 의무는 현재 공식 근거와 적용 여부를 확인한 경우에만 명시한다.

첫머리에서 지금 할 일을 설명하고, 각 문제의 위치·발생 조건·영향·조치 필요성·구체적 행동·조치 시점·완료 확인 방법을 제시한다. “업데이트 필요”, “삭제 보완”, “안내 수정”만으로 끝내지 않는다. “확인 먼저”에는 확인할 설정과 확인 결과에 따른 조치 여부를 붙인다. 자동검사 통과 수는 실제 검사 범위와 함께 제시하고 전체 안전성 판단에 대신 쓰지 않는다.

우선 고칠 문제부터 쉬운 말로 설명한다. 낯선 용어에는 짧은 설명을 붙이고 막연한 활동 이름을 새로 만들지 않는다. 지적 개수를 맞추기 위해 문제나 개선 사항을 늘리지 않는다.

“꼭 해야 하나?”라는 재질문에는 기존 근거부터 재검토한다. 사용자 반응만으로 등급을 낮추거나 처음 답을 지키기 위해 억지로 유지하지 않는다. 판단을 바꾸면 이전 판단, 새 판단, 새로 확인한 사실 또는 기존 해석의 오류를 함께 설명한다. 추가 근거가 없는데 필수와 권장을 오가는 답변을 하지 않는다.

수정했다면 허용할 동작과 차단할 동작을 함께 재시험하고 기존 기능도 확인한다. 실행하지 못한 시험과 그 이유를 구분한다. 요청이 점검뿐이면 결과와 수정 제안에서 끝내고, 실제 수정이나 보고서 파일 저장은 사용자 요청 범위에 따른다.
