# 조치 필요성 판단과 결과 작성

점검을 받은 교사가 “어디가 문제이고, 반드시 고쳐야 하는지, 지금 무엇부터 하면 되는지”를 알 수 있게 보고한다. 짧은 답변에도 조치 필요성과 판단 근거를 생략하지 않는다. 원자료의 프롬프트 수나 활동 수와 무관하게 실제 발견 사항만 보고한다.

## 확인 상태와 조치 필요성을 구분

`문제 확인 / 확인한 범위에서 문제 미발견 / 추가 확인 필요 / 해당 없음`은 무엇을 확인했는지 나타낸다. 이것만으로 조치 필요성이 정해지지 않는다. 예를 들어 영향을 받는 라이브러리가 설치돼 있다는 사실과 실제 배포 환경에서 권고의 발생 조건이 충족된다는 사실은 다르다.

발견 사항의 조치 필요성은 다음 기준으로 판단한다.

| 구분 | 판단 기준 | 결과에 적을 내용 |
| --- | --- | --- |
| 필수 조치 | 확인된 보안 결함을 해결해야 하거나, 적용이 확인된 의무·운영 기준 또는 실제 동작과 안내의 불일치를 바로잡아야 함 | 무엇을 해결해야 하는지, 근거, 언제까지 필요한지. 특정 코드 수정만이 유일한 해법인지는 별도로 판단 |
| 확인 먼저 | 배포 버전·운영 설정·실제 사용 여부 등 중요한 근거가 없어 조치 필요성을 결정하지 못함 | 누가 어디서 무엇을 확인할지, 어떤 결과면 고치고 어떤 결과면 추가 수정이 불필요한지 |
| 권장 개선 | 확인한 범위에서 위반이나 결함은 없고, 관리 편의·추가 방어·운영 안정성을 개선하는 제안임 | 무엇이 좋아지는지와 현재 조치가 필수는 아닌 이유. 안전을 확정했다는 뜻으로 쓰지 않음 |

필수 조치에는 근거의 종류를 명시한다. 기술적 보안 조치를 법적 의무라고 표현하지 않는다. 법적 필수라고 판단하려면 현재 공식 조문·지침, 적용 대상과 조건을 확인해야 한다. 최신 자료나 적용 여부를 확인하지 못했으면 판단을 보류한다.

심각도와 조치 시점도 구분한다. 심각도가 높다는 도구 경고만으로 “즉시 수업 중단”을 요구하지 않는다. 반대로 실제 노출이 확인된 비밀키나 권한 없이 조회되는 학생 자료는 공격 성공을 추가 시연하지 않았다는 이유로 단순 권장으로 낮추지 않는다. 공격을 실행하지 않고도 코드와 요청 경로로 충분히 입증한 사실은 근거로 쓸 수 있다.

## 항목별로 반드시 설명할 내용

1. **문제 위치:** 기능·화면 이름과 해당 코드·설정 위치를 함께 적는다. 파일 링크만 던지지 말고 그 코드가 무엇을 하는지 설명한다. 줄 번호나 설정 이름을 확인하지 못했다면 만들어 쓰지 않는다.
2. **무엇이 문제인가:** 누가 어떤 조건에서 어떤 자료나 기능에 영향을 줄 수 있는지 설명한다. 보안 취약점, 자료 보관 문제, 안내 불일치, 추가 개선을 구별한다. 가정은 가정으로 표시한다.
3. **확인한 근거와 남은 확인:** 코드, 설치 버전, 모의검사, 실제 요청, 배포 설정을 구별한다. “가능하다”와 “직접 확인했다”를 섞지 않는다.
4. **조치 필요성과 이유:** 필수 조치·확인 먼저·권장 개선 중 무엇인지 먼저 쓰고 이유를 설명한다. “보완 필요” 같은 표현만 쓰지 않는다.
5. **지금 할 일:** 코드 수정, 설정 확인, 문서 정정 중 무엇인지 구체적으로 적는다. 사용자 확인이 필요한 경우 실제 메뉴와 확인할 값을 알려 준다. 도구가 권한 내에서 안전하게 확인할 수 있다면 사용자에게 같은 조사를 떠넘기지 않는다.
6. **조치 시점과 임시 대안:** 다음 배포 전, 해당 기능 사용 전, 정기 관리 때 등 근거에 맞는 시점을 제안한다. 전체 사용 중단과 해당 기능의 제한을 구별하고, 판단할 근거가 없으면 시점도 단정하지 않는다. 임시 대안이 효과가 있는지 확인하지 않았다면 확정적인 해결책으로 쓰지 않는다.
7. **완료 확인 방법:** 수정 후 어떤 동작·자료·설정을 확인하면 해결됐다고 판단할 수 있는지 적는다. 정상 동작과 차단할 동작을 함께 검증한다. 확인 먼저인 항목은 확인 결과에 따라 다음 행동을 나눈다.

발견 사항이 여러 개면 첫머리에 `항목 / 조치 필요성 / 지금 할 일` 정도의 짧은 표를 쓰고, 세부 근거는 항목별 본문에 둔다. 긴 설명을 모두 표의 작은 칸에 밀어 넣지 않는다. 항목이 하나면 문단만으로 설명해도 된다.

마지막에 이번 작업에서 실제 수정한 것이 있는지, 다음 단계에 사용자 결정이 필요한지 밝힌다. 검토만 요청했다면 수정에 착수하지 않는다.

## 혼동하기 쉬운 판단 사례

아래는 판단 방법을 설명하는 가정 사례다. 특정 사용자의 앱에서 확인한 결과가 아니며, 패키지 버전이나 법적 의무를 이 예시로 대신 판정하지 않는다.

### 라이브러리 보안 경고

- 의존성 검사에 경고가 나왔다는 이유만으로 서비스에서 공격이 가능하다고 단정하지 않는다. 반대로 직접 공격을 재현해야만 조치를 권할 수 있는 것도 아니다.
- 실제 설치·배포 버전, 공식 권고의 영향 범위와 발생 조건, 해당 코드 경로의 사용 여부, 적용된 완화 조치를 확인한다. 개발 전용 의존성과 운영에 포함되는 의존성도 구분한다.
- 중요한 조건이 미확인이라면 `확인 먼저`로 보고하고 해당 조건을 적는다. 잠재 영향이 크다면 확인을 우선해야 한다는 이유도 설명한다.
- 영향 조건이 충족되고 유효한 방어 조치가 없다면 `필수 조치 — 보안`으로 보고한다. 패치, 해당 기능 비활성화 등 검증 가능한 대안을 제시하고, 특정 버전을 권하면 공식 권고와 호환성을 확인한다.
- 영향 대상이 아니거나 이미 해결된 것이 확인되면 해당 취약점의 조치는 불필요하다고 밝힌다. 별도의 최신화 권장은 실제 보안 결함과 나눠 적는다.

### 활동 삭제와 임시 자료 정리

- 활동 삭제 함수에 연관 자료 삭제가 없다는 사실만으로 자료가 영구 보관된다고 결론 내리지 않는다. 별도 정리 작업, 자동 만료 정책, 만료 시점, 삭제 후 접근 차단과 운영상 보관 기준을 확인한다.
- 자동 만료 설정을 읽지 못했다면 `확인 먼저`다. 설정의 활성 여부뿐 아니라 대상 자료에 만료 값이 실제로 있는지, 삭제 지연이 보관 기준과 맞는지도 확인할 항목에 포함한다.
- 이미 다른 방법으로 필요한 시점에 정리되고 접근도 제한된다면 동일한 삭제 코드를 추가할 필요가 없을 수 있다. 관리 편의를 위한 변경이면 `권장 개선`으로 구분한다.
- 보관 기준을 넘겨 실제 자료가 남거나 삭제 후 권한 없는 접근이 가능하다면 그 확인된 문제를 해결해야 한다. 목표는 정리·접근 제한이며, 특정 함수에 코드를 추가하는 것만을 필수 해법으로 지정하지 않는다.
- 완료 확인은 가상 활동 삭제 후 연결 자료의 잔존·접근 가능 여부와 필요한 시간 경과 후 정리 결과로 제시한다. 운영 학생 자료를 임의로 지우며 시험하지 않는다.

### 실제 전송과 개인정보 안내

- 저장 버튼을 누르기 전 글이 서버로 전송된다는 사실과 실제 안내문의 설명을 각각 확인한다. 개인 식별 가능성, 대상 사용자와 활성 조건도 구분한다.
- 실제 동작과 안내가 충돌한다면 불일치 내용을 구체적으로 적고 `필수 조치 — 운영 안내 일치`로 분류할 수 있다. 이 분류 자체가 법적 의무의 판정은 아니다.
- 안내를 실제 처리에 맞추거나, 불필요한 전송을 없애 안내대로 동작하게 하는 대안을 비교한다. 과도한 정보 수집 자체가 문제일 수 있는데 안내문만 추가하면 해결된다고 하지 않는다.
- 실제 사용 여부나 전송 내용이 확인되지 않았다면 `확인 먼저`다. 단순히 문장을 더 읽기 쉽게 바꾸는 제안은 실제 안내 누락과 구분해 `권장 개선`으로 보고한다.
- 완료 확인은 가상 입력으로 확인한 전송 내용·시점·열람 대상·보관과 삭제 방식이 안내와 일치하는지 비교하는 방식으로 제시한다.

## 보고 전 확인

- 사용자가 다시 “그래서 꼭 해야 해?”라고 묻지 않아도 조치 필요성과 근거가 보이는가?
- “코드를 바꿔야 한다”와 “현재 설정부터 확인해야 한다”를 구분했는가?
- 필수라는 판단에 근거와 발생 조건이 있고, 불명확한 부분은 확인 먼저로 남겼는가?
- 확인 결과에 따라 조치가 불필요해지는 경우도 설명했는가?
- 검사 통과 수의 대상과 한계를 밝혔고, 미실행 시험을 통과로 계산하지 않았는가?
- 누구의 앱에서도 반복되는 막연한 권고 대신 지금 확인할 위치와 완료 기준을 제시했는가?
